# Root versus non-root execution of Candidate A

2026-10-22. Exact target D.1.6.4/API22/ARM32. Local static assessment; no vehicle operation. [Recovery](RECOVERY-FIRST-PLAN.md) comes first. Neither root acquisition nor a modified-AA test is recommended on current evidence. No newer-unit reference is required.

## What root would and would not solve

**Does root alone allow a self-signed replacement of com.honda.androidauto.projection.sink while retaining android.uid.system? No.** Normal PackageManager installation still compares existing package and shared-user signatures. Root as the submitting UID does not provide the Windriver signing key. The matching PMS contains signature errors -7/-8 and trusted-system-directory shared-user mismatch -104. A self-signed APK is not compatible merely because its manifest requests UID1000.

Root could potentially execute different code *inside the already-authorized AA process* or change the files it sees after PMS has registered stock identity. That is a different mechanism from an accepted self-signed package replacement. It still requires effective capabilities, SELinux permission, correct runtime/class loading and reliable cleanup. Globally changing signature enforcement or shared-user records would be an additional dangerous change, not a benefit automatically conferred by root, and is excluded.

The existing A/B APKs are unsigned offline artifacts with META-INF signing records deliberately removed. Candidate A changes primary VideoMode1280x688 to1920x720 and preserves229dpi/60fps/fallback. It is not a prebuilt runtime hook, a privileged helper or an installable OEM update. [Byte report](fullscreen-candidate/dex-patch-report.json).

This unit uses **ART** (`libart.so`, dex2oat), with local OAT/DEX checksum implementations. Android5 ART does not establish a modern JVMTI attach/hot-redefinition path. DEX byte offsets in the patch report are not addresses of native compiled instructions. Loaded classes, AOT code, inlining, caches and instruction-cache coherence must be handled by any runtime mechanism.

## Root-enabled mechanisms, evaluated separately

“Stock intact” below means original on-disk bytes can remain intact by design; it is not a demonstrated recovery guarantee. Every row requires a real authorized execution entry, which is currently missing.

| Mechanism | Android5 applicability / identity | SELinux, cache and scope issues | Stock intact? Restart and rollback |
| --- | --- | --- | --- |
| Patch negotiated configuration in AA memory before GAL registration | Best scope in principle: change only the primary configuration construction or registration values. Runs under existing process identity; no package re-signing needed. Root not logically necessary if an authorized in-process helper exists. | Need exact object lifetime/call interception before registration; current hook not built. Ptrace/root caps and MAC or a real signed in-process runner needed. A child ClassLoader with duplicate names is not method replacement. | Yes. With a one-shot hook removed, target process termination discards it. Normal app state/logs may still be written. AA clean restart is framework-capable, untested as this hook's recovery. |
| Ptrace/process memory editing / method replacement | libc/ART primitives exist. Potentially transient, but no authorized attach route or tested patcher. Root could remove some DAC/dumpable barriers only with appropriate caps/domain. | Cross-process ptrace policy, ABI, maps/ASLR, stop/resume, AOT/inlining and safe code update all matter. Editing cached DEX alone may leave compiled code unchanged. No live addresses inferred from historical PID2442. | Yes if confined. Detach alone does not undo edits; remove injector/reapply trigger, then discard the target process. A kernel exploit used to obtain access adds independent recovery risks. |
| Bind mount alternate APK over active pathname | Linux bind-mount approach could make an existing source path resolve to alternate bytes without physically changing `/system`. It is not a normal signed install. PMS may retain original in-memory identity, but this particular load/verification/caching behavior is not demonstrated. | Requires usable CAP_SYS_ADMIN/domain, correct namespace and propagation. ART may use original/precompiled OAT, reject checksum mismatch or compile/write cache. Package resources/native paths must remain consistent. A later PMS rescan/boot sees different state than a simple target launch. | Potentially. Must stop the experiment, unmount in **the same relevant namespace**, then start stock. Process restart alone does not undo a shared/global mount. Reboot normally drops volatile mounts only if no init/persistent trigger recreates them; this is not demonstrated vehicle recovery. |
| Bind mount over `classes.dex` | Only possible if the runtime actually reads a separate DEX filesystem path. The current classes.dex is a **ZIP entry inside the APK**, not a mountable file path. | Cannot bind onto `AndroidAuto.apk/classes.dex`. Need whole-APK substitution, controlled external code path or runtime hook. | No ready route. No rollback command for a nonexistent mount target. |
| Bind mount entire package directory | Could present alternate APK/native directory together. Still not an ordinary signed package update and not proven to be accepted by this ART/PMS state. | Wider surface than one APK; symlink topology, relative dependencies, labels and active nativeLibraryDir must match. Can mask stock binaries/dependencies and affect processes sharing the namespace. | Original bytes could remain. All mounts must be unwound in reverse order before stock relaunch; not just deleting the replacement directory. Higher risk than a confined configuration hook. |
| Mount namespace override | A truly private target namespace could scope file views to AA, ideally disappearing when its last process dies. Android5 app storage isolation code does not prove a particular helper can enter/create the needed namespace. | Need kernel namespace config, setns/unshare capability, mount propagation, correct zygote child timing and proof no shared consumer is altered. Joining a namespace with surviving tasks or open helper references defeats assumed process-lifetime rollback. | Potentially. Target+helper teardown could remove the private namespace; exact sequence unimplemented. Never alter zygote/system_server namespace to test this. |
| tmpfs-backed alternate APK/helpers | tmpfs is observed and could keep alternate bytes out of persistent storage. tmpfs alone does not put the file in AA's classpath. | Mount/exec permissions, labels, memory budget and OAT output are separate. Moving an APK to RAM does not relax signature checks for normal PM installation. | Yes by design. Unmount after stopping users; reboot loses RAM contents, but startup properties/cache/app-data changes need their own undo. |
| overlayfs | Not in the captured filesystem list; kernel config/module support unknown. | Requires kernel support, mount privilege and allowed labels/propagation; upper/work directories introduce extra state. | Conceptual only, no practical path established. No overlay-based test recommended. |
| DEX/ClassLoader/ART classpath injection | PathClassLoader can load code in a process that deliberately invokes it; LoadedApk includes installed and instrumentation paths. Root can sometimes facilitate a hook, but does not automatically change already-defined HMI classes. | Parent-first lookup, same-name type identity, boot/app classpath, Application lifecycle, JNI registration and initialization timing. No universal Android5 hot-replace API identified. | Potentially if entirely in process. A fresh stock launch is the undo only after the injection entry is removed. |
| Standalone app_process / alternate APK path | A root launcher could choose a UID/domain only through appropriate authorized mechanisms; `app_process` launched as shell stays shell. A synthetic process is not automatically the registered AA application. | App binding, Binder token, resources, data directory, services, USB/GAL ownership, runtime/native dependencies and MAC all need reconstruction. PMS still applies for normal install. | Stock can remain, but usefulness as a faithful AA test is unproved. Kill the synthetic process only after releasing projection resources; may require target lifecycle cleanup. |
| Wrapper startup / LD_PRELOAD-like hook | Real old Zygote `wrap.*` property path exists. WrapperInit executes a command before app_process. A correctly allowed native preload could hook early startup on some paths; this linker/runtime path is not validated here. | Not a stock Android5 HMI replacement mechanism by itself. Secure-exec/env handling, root drop, domain transition, readable/executable location, ARM ABI and ART JNI/inlining must be checked. Replacing Java HMI logic with a preload needs an actual hook. | Stock can remain. Clear/restore wrapper trigger **before** restarting; stop helper/release mounts. Process restart while key remains set reapplies it. No safe wrapper implementation exists yet. |
| Native GAL/library interception | Could in principle intercept registration/negotiation without changing Java method code. Root not needed if a qualifying permitted loader already exists. | Need exact JNI/ABI/function boundary and full negotiated structure, as well as loader/search paths, RELRO/protections and ownership of the receiver. Fixed library names alone do not establish override. | Potentially process-only. New launch must load unmodified original library; persistent path or shared mount must first be restored. Not implemented. |
| Modified dalvik-cache/OAT files | This runtime uses ART; method execution may come from compiled OAT and boot images. Checksums/relocations must match runtime expectations. | Persistent cache modifications, stale compilation, shared cache dependencies, wrong native instruction offsets and regeneration make this a poor first test. No reason to edit a boot image/shared ART cache. | APK may remain intact but effective code may not. Restoring one OAT or rebooting is not guaranteed to regenerate the right state. Excluded. |
| chroot / isolated test userspace | Useful as an offline semantic experiment only if matching runtime/dependencies can be provided. Root/chroot does not emulate Android app registration or vehicle services. | Binder, USB, display, SELinux, namespaces and existing receiver ownership remain shared/missing. Granting system identity is not a consequence of chroot. | No faithful first vehicle AA test demonstrated; teardown is not proof of subsystem cleanup. |

Do not equate “a mount disappears on reboot” with “safe to reboot a damaged head unit.” A transient mount test can still write persistent ART/PMS/app state or prevent access to cleanup. The method must prove that those effects are absent or recoverable before testing.

## Non-root routes, reconsidered with current services

| Route | Evidence | Remaining obstacle / conclusion |
| --- | --- | --- |
| OEM-signed instrumentation | AMS checks installed runner/target signatures; ActivityThread loads authorized runner code. Existing test-runner libraries are not installed AA-targeting harnesses. Seven newly collected manifests have no instrumentation. | Need a genuine compatible harness and a precise one-shot pre-GAL hook. Adding a self-signed helper fails trust. Conditional best isolation model; not an available test. |
| `wrap.com.honda.androidauto.proj` | Exact31-character truncated key derived from this ZygoteConnection implementation. ## Ranking by requested reversibility criteria

These rank designs for further static work, **not recommended live tests**. No route passes the recovery/entry gates today.

| Preference | Design | Persistence class / requirements |
| --- | --- | --- |
| 1 | Existing authorized one-shot in-process configuration hook | No helper installation/property/mount; code changes disappear with AA process. No such helper identified. |
| 2 | OEM-signed existing instrumentation with bounded hook | Process-lifetime change, but instrumentation itself interrupts target and must not reapply. No compatible harness available. |
| 3 | AA-only wrapper with permitted RAM helper and reversible nonpersistent property | Reboot-lifetime property; explicit key/helper cleanup before restart. Setter/execution/hook unproved. Does not automatically revert on AA termination. |
| 4 | Installing an OEM-signed narrow helper | Requires persistent package/data install and valid signing; removal/data cleanup must be separately defined. No helper available. |
| 5 | Already-authorized temporary root plus AA-only memory hook/private namespace | Could avoid disk changes but root acquisition, MAC, namespace and hook add risk. No temporary root available; recovery gate unmet. |
| 6 | Global bind/tmpfs substitution or OAT manipulation | Broader namespace/cache/persistent-state risks. Not suitable before memory-only entry is resolved. |
| 7 | Verified `/system`, boot, policy or signature-enforcement changes | Requires independent image recovery; currently unacceptable. |

An ideal rootless hook beats obtaining root for its own sake. Root could materially help with mount/attach permissions, but currently adds an unproved acquisition and recovery problem. The next decision should be based on D-series recovery/entry evidence, not on a newer-unit code comparison.
