# Recovery first: 2021 RDX D.1.6.4

2026-10-22. Exact target: Android5.1.1/API22, ARM32, `com.honda.androidauto.projection.sink`, shared UID1000. This pass used existing local files only. No ADB, network, service invocation, root attempt, property change, restart, installation, staging, recovery or flashing operation was performed. A 2022+ reference is optional and is not a prerequisite in this plan.

**Decision: the available evidence does not establish a recovery path sufficient to authorize root or modified-AA testing.** A saved APK, two system partition names and a reset menu do not establish recovery from boot failure. Process-only tests could eventually need less recovery coverage than partition changes, but their entry and cleanup mechanisms are not implemented or demonstrated either.

## Evidence levels

| Level | Meaning in this report |
| --- | --- |
| A — demonstrated | A recovery was actually completed on this exact unit, with before/after evidence. |
| B — statically inferred | A concrete recovery branch exists in available matching code; its prerequisites and limitations are identified. No vehicle recovery trial is implied. |
| C — hypothetical | Mechanism, accessibility, payload or applicability is missing. It is not a fallback to rely on. |

**There is no level-A package/system/boot recovery demonstration in the saved record.** The earlier restoration of stock display geometry is not evidence of APK, package-state or firmware restoration. Historical instructions to undo experiments are not proof they ran.

Existing completed work is reused: [deployment trace](DEPLOYMENT-PATHS.md), [current service implementations](current-update-stack/README.md), [temporary execution audit](TEMPORARY-EXECUTION.md). New survey coverage and limits: [evidence index](recovery-root-evidence/README.md).

## Can stock AA be restored without reflashing everything?

**Conditionally yes, in the normal updated-system model; not demonstrated for a custom deployment on this unit.** Keeping the base directory intact and using an accepted normal system-app update gives PMS a specific original to re-enable. That route has code-backed restoration but still needs correct disabled-system state and may discard AA data. It does not accept our unsigned/self-signed Candidate A.

For a genuinely process-only hook, removing the hook and terminating the isolated target should restore the *code source* without firmware flashing. No working entry/hook/cleanup chain is established. If the base directory itself is corrupted or removed, this record contains no demonstrated independent vehicle-side restoration method. A saved APK is useful repair material, not a proven ability to put it back safely under dm-verity.

## Contradictions and evidence quality

1. Saved init.rc/init.environ.rc/init.trace.rc/init.usb.rc are **zero bytes**, including their archive copies, while saved device listings show nonzero originals. They cannot prove startup triggers, adbd flags, SELinux transitions or reset wipes. Obtain actual nonempty originals later through an authorized read-only channel; do not infer their contents from Android defaults.
2. Kernel command line/ro.boot.selinux say permissive, while current runtime evidence reports enforcing. Identify the effective policy/startup transition; boot text does not waive runtime enforcement.
3. Boot/system/environment pair names suggest redundancy, but no boot-success/fallback algorithm is established. Obtain U-Boot/environment/state-machine/utility implementations and actual selectors before classifying redundancy as recovery.
4. file_contexts includes **commented** old block-label examples (including persistdata on p2); command line names p2 as root and runtime mount aliases do not resolve all numbered targets. The apparent overlap is unresolved, not a valid write map. Need real by-name symlinks and boot filesystem layout.
5. Generic RecoverySystem and Honda `factoryreset`/`develupdate` are separate code paths. Native dispatch is missing; do not silently equate them.

## Recovery gate

For a process-only test: require verified stock source/native hashes, an implemented audited hook that makes no persistent configuration changes, independent control access, a cleanup sequence that removes the trigger **before** target relaunch, and evidence that stock AA can be relaunched without that hook. No vehicle test is authorized by this document.

For mount/package/root/boot experiments: additionally require consistent package/partition state as applicable, exact recovery media plus authentication/eligibility, understood boot selection/fallback, and a proven independent recovery channel. **These gates are not met.** Compare methods in [FIRST-LIVE-TEST-CANDIDATES.md](FIRST-LIVE-TEST-CANDIDATES.md); do not run them.
