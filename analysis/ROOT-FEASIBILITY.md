# Root feasibility: exact D.1.6.4 platform

2026-10-22. Static/local investigation only. No root attempt, exploit, device command, property set, reboot, image modification or SELinux change. [Recovery gate](RECOVERY-FIRST-PLAN.md) is not met; **no root test is recommended**. A 2022+ unit is not required for this investigation.

## Root candidates, classified

A=temporary root lost on reboot; B=boot-image-only root; C=persistent root; D=exploit-dependent runtime root; E=unsupported/speculative. A describes persistence, D describes the acquisition dependency: an exploit yielding transient root could be A+D. Preference A>B>C does not override the recovery gate.

| --- | --- | --- | --- | --- |
| Production adbd root control — E | adbd compiled/configured to retain UID0 and an authorized root-mode trigger. Existing response contradicts availability. | No proven privilege. A service flag alone is insufficient; do not change it. | Shell_prop policy access is not adbd implementation support. Root-domain rules would still matter. | ADB restart could interrupt control; no demonstrated root/rollback. Repeating failed `adb root` has no new basis. Not useful as an available path. |

**Temporary root feasibility: unestablished.** No supported temporary-root path was found. It is not proved impossible; important binaries, init/boot artifacts and effective policy details are missing. Neither root nor a root exploit should be a prerequisite assumed by the next test plan.

## Native/service audit, without executing code

- EngineeringAccessService/DiagnosticsSessionControl manage vehicle diagnostic sessions; validation controls MOST/MOCCA firewall. Neither is an Android root/debug-shell loader. JNI diagnostics libraries expose fixed hardware and Bluetooth tests. Their root-related words do not establish arbitrary execution.
- SoftwareUpdateService dispatches regular/factory state-machine work; FactoryFlashing rewrites factory configuration; Transport coordinates ECU inventory/programming. `swupdate` utility clients expose boot/system/status setters and getters, not an identified general command executor. Java setters check WRITE_UTILITY; actual native Binder enforcement remains unaudited without its implementation. No methods were called.
- RedBend Ipl.execCommand is a native-callable `sh -c` helper running in its process context; ClientService is a system-UID app, not automatically UID0. No arbitrary shell-to-helper reachability established. Authenticated native input reachability is still a gap. Debug/release engines both contain security routines.
- `Util.setPersistentProperty(String,String)` and FactoryReset's reset.prop parser are genuine generic property-writing functions **inside existing privileged code**, not proven exported property-setting Binder endpoints. Factory reset invokes extensive persistent operations. It must not be repurposed as a wrapper setter.
- libdevelupdate contains boot/environment/system/persistdata image paths and verification routines. libswupdate exposes utility status/partition field functions. `/sbin/state_machine`, `/sbin/devupdate_bin`, init, adbd, factoryreset and actual bootloader/environment contents are not locally available. Root native process/listing evidence is not their decompilation.
- Local libart, compiler, libc, libcutils and libselinux were parsed as ARM ELF data. Exports include ptrace/exec/mount/classloading-related primitives and ART OAT/DEX checksum machinery. These are implementation building blocks, **not** privilege-escalation endpoints or complete function audits. [Native inventories](recovery-root-evidence/native-summary.json).

## Partial SELinux structural evidence

Saved policy SHA256 `58F4825C599280DC408ECEE0254B1DA78C6F540304EB40BDBC51898B3D53A9A6`, policy version26. An offline structural extractor identified500 contiguous type/alias records and an AVTAB-shaped table of6934 records at byte53583, validating every record's type IDs/key shapes. It extracted selected class permission names and direct records; [raw structural result](recovery-root-evidence/policy-structure.json).

Notable **allow-shaped** entries (`specified=1`, property_service set): system_app→default_prop at byte66439; system_server→default_prop at byte126535; shell has direct debug_prop, shell_prop, powerctl_prop and ctl_dumpstate_prop entries. **No effective-access verdict is claimed:** attribute membership, constraints, conditional tables, permissive maps and live policy reload were not fully decoded or independently validated. Missing direct shell→default_prop is not a proof of denial. Non-allow audit masks and transition data must not be interpreted as allow permissions.

This narrows the question to finding an already-authorized, narrow property writer and executable helper; it does not make one available. `wrap.com.honda.androidauto.proj` maps to default_prop, while service.adb.root maps to shell_prop. A root UID or system-app signature does not authorize arbitrary behavior outside its effective domain. No setprop/SELinux probe was run.

## What would change the root decision?

First obtain the same-unit recovery materials and a credible independent restore procedure in [RECOVERY-FIRST-PLAN.md](RECOVERY-FIRST-PLAN.md). Then prioritize actual nonempty init/hardware rc/fstab, exact adbd/init/state_machine/utility/devupdate/factoryreset implementations, full named partition/environment map, kernel configuration/source patch evidence and authoritative effective policy analysis. These can establish whether a supported transient route exists; they do not authorize a root trial. No CVE or exploit is inferred from a version string.
