# M5 permission only — SOURCE/DESIGN, DO NOT RUN BEFORE M4 PASS

Prepared under `m5-permission/`, package `com.rdx.fullscreen.m5permission`, `.PermissionService`. Java7 source compilation PASS (log under source-host-check); **no APK built or live test authorized.** A completed M4 PASS and explicit separate M5 approval are prerequisites; an intent boolean is an operator acknowledgment, not proof of that PASS.

The source requires action `REQUEST_ONCE_AFTER_M4_PASS`, boolean m4_pass_confirmed=true, and exact device_name/vendor_id/product_id matching the M4-observed device. It enumerates, checks hasPermission, returns if already granted, otherwise issues one requestPermission using a package-targeted one-shot PendingIntent and registered result receiver. It checks returned device and actual hasPermission, logs, then stops. START_NOT_STICKY; duplicate active requests are ignored; timeout45sec, no retry. No open/claim/control/bulk/release/reset, AOA/GAL/TLS/media, credentials or default-handler registration. Source needs an independent build/audit before any live use.

SystemUI's USB permission Activity can resume even though our package has no Activity. Monitor APP_LAUNCHED, GalPrefs, ActivityManager, SystemUI, RDX.M5 and dumpsys usb. Do not promise lifecycle neutrality or assume the permission UI is available outside lock task. Do not manipulate lock-task policy. Decline/timeout/missing UI/wrong identity/detach means STOP; never grant through hidden MANAGE_USB/Binder APIs.

A permission callback flag alone is insufficient: confirm hasPermission on the same still-enumerated device. Permission is not interface ownership. Re-enumeration may remove the grant. Do not check "always use" or change the USB default handler. A timeout/Service stop does not guarantee that a SystemUI dialog already shown is dismissed or that a later user decision cannot update Android's grant state; close that dialog through its normal UI and record any grant/detach state. Uninstall is not claimed to undo all platform/OEM bookkeeping.
