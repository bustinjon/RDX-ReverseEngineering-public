## Handshake accounting concern narrowed

The earlier options report flagged `bytesWritten = handshakeSink.position()` as suspicious. Inspecting the sink end-to-end resolves the ordinary-path concern: `OpenSSLBIOSink.position` is a **read/drain cursor**, not the count written into the ByteArrayOutputStream. Native output grows buffer size; `available = size - cursor`. A completed drain resets both. Handshake unwrap may therefore report consumed peer bytes and zero destination bytes while internally staging outbound TLS bytes. NEED_WRAP then exposes those bytes through wrap. The current driver can perform both operations within one logical pump and preserves the final flight.

The new test scripts that pattern into the **actual MemoryTlsEngine driver** and checks exact returned output. This is stronger than assuming all produced TLS output must emerge directly from unwrap, but weaker than executing Android native code. No ordinary-path counter mismatch is established by the saved source/DEX. This chronological clarification supersedes the suspicion, not the entire earlier evidence report.

## Close path: DEX-confirmed concern, not a measured platform failure

[closeOutbound excerpt](api22-qualification-20261024-155013-513/OpenSSLEngineImpl-closeOutbound.dex.txt) starts at code offset0x016ef0. Instruction001d calls shutdownAndFreeSslNative;0026/002f assign CLOSED/CLOSED_OUTBOUND;002b calls shutdown again. [free](api22-qualification-20261024-155013-513/OpenSSLEngineImpl-free.dex.txt) calls SSL_free and zeroes the pointer. [wrap](api22-qualification-20261024-155013-513/OpenSSLEngineImpl-wrap.dex.txt) returns CLOSED/0 before normal sink draining when closed. Shutdown uses SSL_shutdown_BIO with the current pointer.

Thus any generated close output appears inaccessible through the normal next-wrap path. The second shutdown sees a zero pointer on the established path. Its exact JNI exception/guard behavior was not executed; do not infer a crash. This is not a demonstrated application-encrypt/decrypt failure and does not trigger automatic native-backend implementation. A reproducible Android close-only limitation might permit controlled abort policy rather than replacing all TLS mechanics.
